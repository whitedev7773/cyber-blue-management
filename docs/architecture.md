# 구현 구조

## 실행 경로

HTTP 업로드 → 크기·경로 제한 → 입력 목록 생성 → 고정 계획 → 전문 작업 병렬 실행 → 동일 규칙 재평가 → 보고서 통합 → SQLite 저장.

총괄은 `run_review`, 전문 작업자는 `specialist` 함수입니다. 주제 팀은 `TEAMS`, 점검 카탈로그는 `POLICIES`에 선언됩니다. LLM이 팀을 생성하거나 코드를 실행하지 않습니다. 주제별 작업은 읽기 전용 입력을 공유하고 독립 결과를 반환합니다. 작업 수와 동시성이 고정되어 있습니다.

## API

| 메서드 | 경로 | 내용 |
| --- | --- | --- |
| GET | `/api/session` | 현재 프로세스의 로컬 변경 요청 토큰 |
| GET | `/api/runs` | 최근 100개 실행 목록 |
| POST | `/api/runs?name=security.config.json` | raw bytes 업로드, 202 및 실행 ID |
| GET | `/api/runs/{id}` | 진행 이벤트 또는 최종 보고서 |
| POST | `/api/runs/{id}/review` | `finding_id`, `state` 변경 |
| DELETE | `/api/runs/{id}` | 완료·실패 실행의 논리적 삭제 |

변경 요청에는 `X-Aegis-Token`이 필요합니다. 목록·조회는 루프백 사용자용이며 다중 사용자 인증이 아닙니다. 700ms 폴링을 사용합니다. 진행 상태는 queued/running/completed/failed입니다. 전문 작업 접수와 보고서 제출 기록을 남깁니다. 별도 메시지 브로커나 작업 재개는 구현하지 않았습니다.

## 결과 계약

- `judgment`: policy_mismatch / needs_context / external_unverified
- `review_status`: open / accepted / deferred / dismissed
- `patch_status`: not_applied
- `proposed_patch`: JSON Patch 연산 또는 null
- `coverage`: 파일 수·설정 파일 수·점검 수·통과 수·판단 불가 수
- `skipped`: 지원하지 않거나 파싱할 수 없는 파일과 사유
- `reports`: 각 전문 작업의 점검 목록 및 발견 목록

보고서에 원본 설정값을 복사하지 않습니다. 패치는 사전에 선언된 기준 값만 제안합니다. SARIF 원본 위치를 추측하거나 업로드 밖의 경로를 열지 않습니다.

## 다중 모델 검토 확장 설계 — 미구현

LLM 연동은 기존 발견 사항의 설명·분류·수정안 검토에 한정한 어댑터로 추가할 수 있습니다. 탐지 도구 실행 권한과 모델 출력을 분리합니다.

입력: 발견 ID, 유형, 최소화된 근거, 성립 조건, 제안 변경.
출력: 검토 의견, 누락된 조건, 수정안 주의점, 근거 참조.

프로필에는 제공자·모델명·시간 한도·응답 크기·허용 역할을 명시합니다. 비밀 키는 서버 환경에서 읽고 DB나 브라우저에 저장하지 않습니다. 외부 전송은 기본 비활성화합니다. 모델 응답은 신뢰하지 않는 JSON으로 검증하며 실행 명령으로 해석하지 않습니다. 모델 동의 수를 취약점 확정이나 패치 검증으로 취급하지 않습니다.

## 알려진 한계

- 고정 정책만 검사하므로 소스 데이터 흐름이나 실제 런타임 보안 상태를 알 수 없습니다.
- 규칙 재검증은 독립 분석이 아닙니다.
- SQLite 이력은 변조 방지 감사 로그가 아닙니다.
- DB 자동 보존 기간, 모델 비용 관리, 작업 취소, 다중 사용자 인증은 미구현입니다.
- 폴링 UI이며 파일 전체 코드 뷰어는 없습니다.
- 세션 유휴 시간 30분은 샘플 기준입니다.
- 일반 인터넷 서비스로 배포하려면 인증, 업로드 쿼터, 보존 정책 및 운영용 HTTP 계층이 필요합니다.
